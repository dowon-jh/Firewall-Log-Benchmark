# Logstash worker별 벤치마크 결과

## 1. 실험 목적과 자료 범위

동일 방화벽 로그 1,000,000건을 파싱·집계하는 Logstash에서 worker 수를 1·4·8로 바꿨을 때, 측정 소요 시간·구간별 EPS·자원 사용량·집계 결과가 어떻게 달라지는지 비교했습니다.

이 문서는 기존 8쪽 벤치마크 보고서, worker별 실행 화면, worker 1 집계 CSV를 대조한 기록입니다. 문서 작성 시 새로 수행한 작업은 CSV 재집계이며, ELK 벤치마크를 재실행하지는 않았습니다.

| 근거 | 확인한 범위 |
|---|---|
| 벤치마크 보고서 | 환경, 변인 통제, 파싱 수정, 측정 수치, 리소스 범위 |
| worker 1 결과 화면 | EPS 요약, 시작·종료·소요 시간, 입력·출력·실패 건수 |
| worker 4·8 실행 화면 | 초기화, API 대기, 7회 샘플링, 집계 합계 대기, 시간·EPS 요약 |
| worker 1 집계 CSV | 전체 행 수, 이벤트 수 합계, 고유 키 수, 동일 키의 복수 행 여부 |

원본 입력 파일, Docker Compose·Logstash 설정과 측정 스크립트, 각 실행의 지표 CSV·JSON 전체는 이번 자료 폴더에서 확인되지 않았습니다. 표의 값은 실제로 확보한 원시 지표 파일에서 다시 계산한 값과 구분해 읽어야 합니다.

인덱스·볼륨 초기화는 동일 파일을 처음부터 처리하기 위한 실험 절차입니다. 운영 데이터에 적용할 유지보수 절차가 아닙니다.

호스트 사양·Docker 자원 제한·캐시 상태·입력 해시가 고정됐는지는 확인할 수 없습니다. 최종 결과는 worker별 한 실행씩 제시돼 있어, 반복 측정 평균이나 분산은 계산하지 않았습니다.

## 3. 지표 정의와 시간 범위

### 측정 소요 시간

실행 화면의 `START`부터 `END`까지의 차이입니다. worker 4·8 화면에서는 다음 단계가 포함됩니다.

```text
START
  → Logstash 컨테이너 시작
  → API 준비 대기
  → 지표 샘플링
  → 입력 파일 완료 표시 대기
  → Elasticsearch sum(event_count)=1,000,000 확인 대기
END
```

따라서 이 시간을 순수 필터 처리 시간이나 정상 상태의 처리 지연시간으로 해석하지 않습니다. 화면에서는 최종 count 수집이 END 뒤에 수행됩니다.

### 샘플링 구간 EPS

```text
EPS = (나중 events.in - 이전 events.in) / 두 관측 시각의 차이(초)
```

보고서의 AVG/MIN/MAX는 처리 중 일부 구간의 EPS 요약입니다. 입력 1,000,000건을 START~END 시간으로 나눈 처리율과 같지 않습니다.

샘플링 설정은 10초 간격이지만 실행 화면의 실제 관측 간격은 API 호출·지표 수집 지연 등에 따라 더 깁니다. worker 1 요약 화면에는 EPS 구간 5개가 보이고 worker 4·8 요약에는 각각 6개가 보입니다. 이를 동일한 7개 EPS 관측값이라고 표현하지 않습니다. 전체 원시 샘플이 없으므로 요약값은 화면·보고서 기재값으로 제시합니다.

### 건수 대조

- `input count`: 원본 파일 줄 수
- `output count`: Elasticsearch에 저장된 집계 결과 행 수
- `sum(event_count)`: 결과 행에 누적된 이벤트 수의 합계
- `failed count`: 실패 전용 인덱스의 문서 수

여러 입력을 한 행으로 집계하므로 output count와 input count는 직접 같은 값이 될 필요가 없습니다. 반면 이벤트 합계 일치만으로 이벤트별 누락·중복, 키별 분배, 시간 구간별 정확성을 모두 입증할 수는 없습니다.

시각은 실행 기록의 표시값입니다. 원본 기록의 타임존 설정은 별도로 확인하지 않았습니다.

- worker 1→4: 소요 시간 238초 감소, 약 58.0% 감소. 샘플 구간 AVG EPS는 약 2.97배.

- worker 8이 이 기록에서 가장 짧은 시간을 보였지만, 처리 결과의 동일성 검증과 반복 실행 없이 최적 운영 설정을 결정하기는 어렵습니다.

## 5. 입력·출력·실패 건수

| worker | input count | output count | sum(event_count) | failed count |
|---|---:|---:|---:|---:|
| 1 | 1,000,000 | 511,500 | 1,000,000 | 0 |
| 4 | 1,000,000 | 261,502 | 1,000,000 | 0 |
| 8 | 1,000,000 | 244,085 | 1,000,000 | 0 |

확인한 것은 **실패 인덱스 건수 0과 이벤트 수 합계 일치**입니다. worker별 output count가 다른 원인은 현재 자료에서 확인하지 못했습니다. 입력 시각 순서, 집계 맵의 유지·만료, flush 시점, 병렬 처리 설정은 확인할 후보이며 입증한 원인이 아닙니다.

## 6. worker 1 CSV 재검증

worker 1의 압축 CSV 전체를 읽어 아래 값을 다시 계산했습니다. 행 수가 보고서의 worker 1 output count와 일치합니다.

| 항목 | 재계산 결과 |
|---|---:|
| 전체 행 수 | 511,500 |
| event_count 합계 | 1,000,000 |
| 고유 aggregate_key 수 | 76,500 |
| 둘 이상의 행에 등장하는 키 수 | 76,493 |
| 전체 행 수 - 고유 키 수 | 435,000 |

마지막 값은 키별 첫 행을 제외한 추가 행의 수이며, **원본 이벤트 중복 건수**를 의미하지 않습니다. 같은 키의 이벤트가 여러 부분 집계 행으로 출력됐을 가능성과 실제 이벤트 중복을 구분해야 합니다.

동일 키를 가진 첫 두 행에는 각각 event_count 1과 2가 기록돼 있고, 같은 20초 구간 안에서 first/last_event_time이 서로 다릅니다. 따라서 현재 CSV는 키당 한 행으로 완전히 합쳐진 결과가 아닙니다.

이는 최종 집계가 키당 한 행이어야 한다는 목표에 대해 추가 확인이 필요함을 보여줍니다. 후처리로 같은 키의 건수를 더하는 것만으로 원본 이벤트 단위의 정확성까지 입증되는 것은 아닙니다. 바이트·패킷 합계와 이벤트 시각도 독립 기준값과 대조해야 합니다.

재검산에 사용한 절차는 다음과 같습니다. `csv_path`에는 로컬 worker 1 압축 CSV 경로를 지정합니다. 이 코드는 이번 문서 작성 중 수행한 검산을 설명하기 위한 것이며, 과거 벤치마크의 원본 측정 스크립트는 아닙니다.

```python
import csv
import gzip
from collections import Counter

def audit(csv_path):
    keys = Counter()
    rows = 0
    event_total = 0
    with gzip.open(csv_path, "rt", encoding="utf-8-sig", newline="") as stream:
        for row in csv.DictReader(stream):
            rows += 1
            event_total += int(row["event_count"])
            keys[row["aggregate_key"]] += 1
    return {
        "rows": rows,
        "sum_event_count": event_total,
        "unique_keys": len(keys),
        "keys_in_multiple_rows": sum(n > 1 for n in keys.values()),
        "extra_rows_for_existing_keys": rows - len(keys),
    }
```

worker 4·8의 전체 CSV는 확보하지 못했으므로 동일 검산은 수행하지 않았습니다.

## 7. 리소스 관측값

다음은 보고서에 기록된 샘플 관측 범위입니다. 실행 전체의 평균·절대 최대값이나 메모리 예약 한도를 뜻하지 않습니다.

| worker | Logstash CPU | 컨테이너 메모리 | JVM heap 사용률 | Elasticsearch CPU |
|---|---|---|---|---|
| 1 | 27.19~259.46% | 1.529~1.543 GiB | 34~73% | 0.49~75.25% |
| 4 | 339.25~712.04% | 1.093~1.83 GiB | 39~91% | 0.80~96.63% |
| 8 | 581.38~872.44% | 914.6 MiB~1.595 GiB | 24~88% | 0.64~35.18% |

CPU 값은 Docker stats의 표시값을 옮긴 것으로, 호스트 전체 CPU 사용률로 환산하지 않았습니다. 컨테이너 메모리와 JVM heap은 서로 다른 지표이므로, heap을 1GB로 고정한 조건과 컨테이너 메모리 관측값을 혼동하지 않습니다.

보고서에는 Block I/O 값도 있지만 관측 시점과 누적값 초기화 조건을 원시 자료로 다시 확인하지 못해 직접 성능 비교 표에서는 제외했습니다. JVM GC 통계, Elasticsearch bulk 지연·거절, 디스크 지연 자료가 없으므로 병목 지점을 확인하려면 추가 지표가 필요합니다.

## 9. 결론과 미완료 검증

이번 기록에서는 worker 수를 늘릴수록 측정 소요 시간이 줄었고, 4→8 조건의 추가 감소 폭은 1→4보다 작았습니다. 다만 출력 행 수가 다른 상태이므로, 같은 집계 결과를 유지하면서 성능이 개선됐다고 결론 내릴 수 없습니다.

원본 보고서의 ‘정상’, ‘정확성’이라는 표현은 이 문서에서 **총량 대조 통과** 범위로 한정했습니다. worker 1 CSV 재검증 결과도 이 구분이 필요함을 뒷받침합니다.

추가 검증 순서는 다음과 같습니다.

1. 원본 설정과 입력을 확보하고 입력 파일의 버전·해시·장비 조건 기록
2. 독립 집계로 키·20초 구간별 건수, bytes·packets 합계, first/last 시각 산출
3. worker별 결과를 같은 키로 대조하고 동일 키의 복수 행 발생 지점 조사
4. 순서 정렬·역전·지연 입력과 timeout 조건을 나누어 재실험
5. 결과 일치 조건을 먼저 정한 뒤 반복 측정과 전체 구간 지표 수집
6. Vector·Fluent Bit는 같은 검증 기준으로 별도 실측한 뒤 비교

대체 도구 전환과 최적 worker 선정은 위 검증을 마친 뒤 판단할 항목입니다.
